## Философия управления материалом

### Главная идея

Плита 1200×600 мм — ресурс с конечной стоимостью. Каждый миллиметр, который не попал на фасад и не вернулся на склад пригодным куском — прямой убыток. Система отслеживает судьбу каждого куска материала от момента открытия плиты до завершения фасада.

**Цель** — минимальная суммарная площадь остатков на складе после каждого фасада при полном соблюдении технологических требований.

### Склад как живой ресурс

Ключевое правило: склад обновляется **немедленно после каждого реза**, до перехода к следующему блоку. Если из плиты 1200×600 вырезан блок 800×410, остаток 400×410 немедленно доступен для следующего блока в том же ряду.

Три статуса каждого куска:
- **Создан** — пригодный обрезок (≥ 200×150 мм). Сохраняется в БД, доступен для следующих рядов/фасадов.
- **Создан и переиспользован** — обрезок, тут же использованный в следующем блоке/ряду. В БД не попадает.
- **Отход** — мин. сторона < 150 мм. Не сохраняется, не используется.

### Приоритет выбора материала

Прежде чем открывать новую плиту, система проверяет склад:

1. **Остаток точного размера** — без реза. Максимальный бонус.
2. **Остаток с пригодным обрезком** — рез есть, обрезок годится на склад.
3. **Остаток с негодным обрезком** — только если других вариантов нет.
4. **Новая плита** — когда склад не может помочь.

### Высота рядов и two-pass dead zone оптимизация

Система не делит фасад на ряды по 600 мм механически. `RowHeightForecaster` (CP-SAT) подбирает высоту, при которой складские остатки покрывают максимум ширины фасада без дополнительного реза.

**Жёсткие ограничения:** `MinRowHeight ≥ 300 мм` (v3.7.1; ранее 150 мм). Dead zone (451–599 мм) обрабатывается двухпроходной стратегией:

- **Pass 1 (hard ban):** `h == 600 OR h <= 450` — принудительно. Таймаут: `min(15 сек, baseTimeout × 3)`. Ограничение `maxActiveRows = ceil(H/TileHeight) + 2` предотвращает лишние тонкие ряды
- **Pass 2 (fallback):** если Pass 1 INFEASIBLE — тяжёлый soft penalty `leftover × rowPosWeight × 10`, cap 2 000 000. Солвер предпочитает чистые высоты, но может выбрать dead zone если геометрия окон не оставляет иного выхода

Прочие предпочтения в целевой функции:
- **Отклонение от 600 мм** — линейный штраф, пропорциональный позиции ряда
- **Stock-driven heights** — при покрытии складом ≥ 80% ширины фасада, награда за stock-height удваивается

### Row Sync: синхронизация сеток рядов (v3.6.0)

При обработке нескольких фасадов одного здания горизонтальные швы должны «опоясывать» здание без ступенек. `DxfHeadlessRunner` реализует это через **Row Sync**:

```
Фасад 1 → RowHeightForecaster (свободный, B2 активен, учитывает окна ВСЕХ фасадов)
          → захват syncedRowHeights = [600, 600, 600, 400, ...]
                ↓
Фасад 2 → CreateSyncedRows(syncedRowHeights)  ← RowHeightForecaster пропущен
Фасад 3 → CreateSyncedRows(syncedRowHeights)
...
Фасад N → CreateSyncedRows(syncedRowHeights)  ← Row Sync для ВСЕХ фасадов
```

> **Инвариант углового замыкания:** Все фасады здания **ОБЯЗАНЫ** использовать идентичную сетку высот рядов от Фасада 1. Нарушение приводит к несовпадению горизонтальных швов на углах здания (конструктивный дефект). Stock Flush (независимые высоты последнего фасада) **отключён**, т.к. нарушает этот инвариант.

**Валидация:** `CreateSyncedRows` проверяет каждую границу ряда против окон целевого фасада. При конфликте (граница попадает в зону ± 130 мм от окна) — fallback на независимый `RowHeightForecaster` с логом `[ROW-SYNC WARN]`.

**Адаптивные высоты для dead zone:** Высота от 0 до проёма не кратна 600 мм. `RowHeightForecaster` Фасада 1 подбирает высоты рядов, чтобы остаток около оконного проёма был ≥ 150 мм (two-pass dead zone strategy, § 10.3). Эти адаптивные высоты затем тиражируются на все фасады через Row Sync.

> **Примечание:** Stock Flush (`stockFlushLastFacade = false`) отключён в `DxfHeadlessRunner/Program.cs`. Флаг сохранён в коде для возможного будущего использования при условии решения проблемы углового замыкания.

### Окна: геометрические якоря

Окно создаёт обязательные горизонтальные швы по координатам нахлёста (±20 мм). Фасад делится на три зоны:
- **Ниже окна** — от низа фасада до нижнего нахлёста
- **Зона окна** — боковины слева/справа, проём пуст
- **Выше окна** — от верхнего нахлёста до верха

Порядок обработки: BOTTOM_EDGE → MIDDLE → TOP_EDGE. Обрезки от нижнего ряда немедленно доступны для боковых.

### Целевая функция (v3.7.0 — Variant C)

Солвер минимизирует количество новых плит с поощрением за утилизацию остатков.

**Единственный механизм поощрения — continuous area bonus:**
```
bonus = −(usedRemnantArea × SCALE × RemnantUsageWeight)
```
где `SCALE = 100`, `RemnantUsageWeight = 115` (pass1) / `135` (pass2).

> **Variant C (v3.7.0):** Аудит выявил, что из трёх механизмов поощрения два были мёртвым/дублирующим кодом:
> - `STOCK_BONUS_MULTIPLIER` (SBM) — вносил **0.0001%** от общего бонуса. **Удалён.**
> - `UNUSED_STOCK_PENALTY_FACTOR` (USPF) — дублировал continuous bonus через тот же BoolVar, но в 200 000× слабее. **Удалён.**
> - Continuous area bonus — **79.4%** вклада, единственный реально работающий механизм. **Оставлен.**

**Полная целевая функция:**

| Компонент | Формула | Назначение |
|-----------|---------|------------|
| PRIMARY (row-level) | `Σ_рядов ceil(Σ NewWidth / TileWidth) × TILE_WEIGHT` | Минимизация физических плит |
| Continuous bonus | `−Σ (usedArea × SCALE × RUW)` | Поощрение утилизации остатков |
| Created penalty | `+Σ (createdArea × SCALE)` | Штраф за создание остатков |
| Cut penalty | `+Σ cutCount` | Минимизация резов |

> **Почему высокий мультипликатор (RUW=135) необходим:** Row-level objective использует `ceil()` для подсчёта физических плит. Мелкие остатки не снижают количество плит без сильного стимула. Попытка нормализации бонуса до 5-50× стоимости плиты привела к 13.06% overconsumption — `ceil()` создаёт «потолочный эффект», при котором малые остатки не дают экономии.

После решения — **IntraRowConsolidate** дополнительно снижает фактическое число плит, объединяя мелкие разрезы в одну физическую плиту.

Идеальный результат: склад после фасада содержит только то, что геометрически невозможно было использовать, но будет использовано на следующем фасаде.

## Алгоритм раскладки

### 1. Деление на ряды

- Стандартная высота: **600 мм**
- Допустимый диапазон: **≥ 300 мм** (v3.7.1; ряды < 300 мм недопустимы)
- Финальный ряд: Trim-to-Target (AdjustRowsToTarget)
- Two-pass dead zone: 451–599 мм жёстко запрещены (Pass 1), heavy soft penalty (Pass 2 fallback)

### 2. Генерация паттернов

`PatternGenerator` создаёт варианты заполнения каждого сегмента ряда:
- **Фаза 1:** Только новые плиты (рекурсия с разными offset'ами)
- **Фаза 2:** Sweep 10 мм — каждый остаток пробуется на всех позициях `0, 10, 20 … segmentWidth-rw` с предфильтром (MinBlock, MinRelease). Бюджет Фазы 2 = **1/2 от maxPatterns** (мин. 150 паттернов). Все геометрически совместимые остатки перебираются без приоритизации.
- **Фаза 2b:** Два остатка — sweep первого с шагом 10 мм, второй вплотную за ним. Top-N адаптивный: `max(20, stock/3)`
- **Фаза 2c:** Чередование ≥ 3 остатков (рекурсия). Top-N: `max(25, stock/3)`. Генерирует паттерны `R→T→R→T→R`
- **Фаза 2d:** Пары остатков `(R+R)→T→(R+R)→T`. Top-N: `max(20, stock/3)`. Соблюдает `MaxConsecutiveRemnants = 2`
- **Фаза 3:** Подстановка остатков вместо обрезанных новых плит (точная замена)
- **Фаза 4:** Look-ahead для будущих сегментов (K)

### 3. OR-Tools CP-SAT солвер

Rolling Horizon (по 1 ряду):
- **Row-level objective** (`EnableRowLevelObjective = true`): `ceil(Σ NewWidth / 1200) × TILE_WEIGHT` — корректно моделирует физические плиты
- **Continuous bonus** — единственный механизм поощрения утилизации (Variant C, v3.7.0). `STOCK_BONUS_MULTIPLIER` и `UNUSED_STOCK_PENALTY_FACTOR` удалены как мёртвый/дублирующий код
- Бонус за использование остатков (`RemnantUsageWeight = 115`, pass2 = `135`)
- Штраф за создание малых остатков (< MinBlock) — x2 в PatternGenerator
- **Pre-cut simulation** — предварительно рассчитывает остатки от оконных вырезов и добавляет их в склад до решения текущего ряда
- **Multi-pass**: 2 прохода с разными весами (pass1 = 115, pass2 = 135)
- **Гибридный отбор остатков (B3)**: при > 400 остатках — 50% по площади + 50% по match-score
- **Pre-allocation (C1)**: `EnableRemnantPreAllocation = true` — hints для PatternGenerator
- **Demand boost (A2)**: ранние фасады получают повышенный RUW (boost factor 1.3→1.0 линейно по номеру)
- **Post-optimize (v3.4.1):** до 5 рядов с наибольшим «отходом» (обрезанные новые плиты); кандидаты после отбора сортируются **снизу вверх** (`rowIdx`). Для пере-решения ряда `idx` в склад попадают только **начальные** остатки + остатки, созданные блоками из рядов **строго ниже** `idx` (`SourceBlockId → blockToRow` даёт `srcRow < idx`). Остатки с неизвестным источником в карте блоков **не** подмешиваются — сохраняется хронология снизу вверх. После принятия нового решения обновляются склад, `AllCreatedRemnants`, L-boot элементы и маппинг блоков.
- **Stock filter (v3.6.0)**: геометрический фильтр вместо эвристики — солвер получает **все** остатки, проходящие `CanUseRemnant(r, rowHeight)`. Hard cap `MaxStockForSolver = 400` срабатывает только при аномально большом складе. `[STOCK-FILTER]` лог
- **Бюджет паттернов**: `adaptiveMaxPat = 10 000` на сегмент, таймаут `max(15, base × 3)` сек

### 3a. Intra-Row BinPack консолидация (v3.4.0)

**Проблема:** CP-SAT считает `NewTileCount` независимо для каждого сегмента. Ряд из 4 мелких `[New]` блоков (200+200+200+240 мм) тратил 4 физические плиты вместо 1.

**Решение (`IntraRowConsolidate`):** пост-процессор запускается после коммита ряда, до `UpdateStockAfterRow`:

```
После commit ряда:
  1. Collect: все [New W < 1200] блоки из всех сегментов ряда
  2. Sort: по убыванию ширины (BFD)
  3. BinPack: Best Fit Decreasing → минимум физических плит 1200 мм
  4. Для каждого бина (>1 блок):
       anchor [New] → остаётся [New]
       остальные   → [CutRemnant] из виртуальной цепочки остатков
       ! Проверка C13 перед каждой конвертацией
  5. UpdateStockAfterRow обрабатывает цепочку
  6. Post-cleanup: удаляет дублирующие anchor-width остатки
```

Пример (ряд 4, 4 сегмента с мелкими New):
- **До:** `[New 200]` + `[New 200]` + `[New 200]` + `[New 240]` = 4 плиты, 4 остатка
- **После:** `[New 200]`(anchor) + `[CutRemnant 200]` + `[CutRemnant 200]` + `[CutRemnant 240]` = 1 плита, 1 остаток (360 мм)

**Флаг:** `RollingHorizonEngine.EnableIntraRowConsolidate = true` (по умолчанию включён).

### 3b. Учёт L-boot в отчёте «созданные остатки» (v3.4.1)

Вырезки **L-boot** (`Source = LBoot_CutOut`) добавляются на склад в `ExtractLBootsAndCreateRemnants`. В список **созданных за ряд** остатков (`AllCreatedRemnants` / диагностика) попадают только **новые** L-boot за этот ряд (сравнение множеств ID до/после вырезки). Ранее `UpdateStockAfterRow` дублировал в `createdRemnants` все L-boot, уже лежавшие на складе — это исправлено.

### 4. Обработка окон

| Тип ряда | Поведение |
|---------|-----------|
| Normal | Блоки не затрагиваются |
| BottomEdge / TopEdge | Г-элемент (L-boot) через Boolean Subtraction |
| Middle | Зона проёма пустая, блоки обрезаются |

Эффективный проём: `effLeft = MinX + δ`, `effRight = MaxX - δ` (нахлёст δ=20 мм ВНУТРЬ).

Г-элемент — один блок с Г-образной формой. Вырезанный кусок (оконный проём) → остаток на склад. Обе полки ≥ 150 мм.

### Правила

### Трассировка остатков от ряда к ряду (v3.5.2)

Поле `Remnant.CreatedAtRow` (int) фиксирует ряд, в котором создан остаток:
- Значение `-1` — начальный склад (загружен из БД до начала обработки фасада)
- Значение `≥ 0` — остаток создан в конкретном ряду текущего прогона

Устанавливается в 6 точках: `UpdateStockAfterRow` (Height/Width/HeightCut/WidthCut + narrow-strip rotated) и `SaveCutoutAsRemnant` (L-boot вырезки).

**Диагностические теги** (в `Debug.WriteLine` / `diagnostics.txt`):

| Тег | Место | Описание |
|-----|-------|----------|
| `[ROW-FLOW] Created W×H …` | `UpdateStockAfterRow` | Каждый новый остаток при создании |
| `[ROW-FLOW] Row N: K remnants created` | Основной цикл | Итог ряда — что передаётся дальше |
| `[ROW-FLOW] Row N USED fresh remnant` | `UpdateStockAfterRow` | Использован остаток ≤ 3 рядов давности |
| `[FRESH] Row N Seg S: K fresh → F patterns` | `PatternGenerator` | Сколько паттернов с участием свежих остатков |

### Материальный баланс

Формулы расчёта (единственный нормативный источник):

| Метрика | Формула |
|---------|---------|
| FacadeGrossArea | `W × H / 1_000_000` (мм → м²) |
| WindowsArea | `Σ(w_k.Width × w_k.Height) / 1_000_000` |
| NetInsulationArea | `FacadeGrossArea − WindowsArea` |
| TotalNewMaterialArea | `NewTilesCount × 1.2 × 0.6` |
| OverconsumptionPct | `(TotalNew / NetInsulation − 1) × 100` |
| CuttingEfficiencyPct | `NetInsulation / (TotalNew + Reused) × 100` |
| StockSavingsPct | `Reused / NetInsulation × 100` |

**Перерасход** — главная бюджетная метрика. База 100% = NetInsulationArea (площадь фасада минус окна). Закупка нового материала (TotalNewMaterialArea) включает всё: утепление на фасаде + остатки на складе + отходы. Порог предупреждения: > 7%. Бюджетный лимит проекта: обычно 5-10%.

|----|------------|

| C13 | Макс. 2 коротких подряд |
| C14 | Перевязка ≥ 100 мм |
| C16a | L-boot полка ≥ 150 мм |
| C17a | Middle-ряд: зона окна пустая |

## Headless Runner

`tools/DxfHeadlessRunner` позволяет запустить pipeline без AutoCAD:
- Текстовый парсер DXF (без внешних библиотек)
- `RollingHorizonEngine` с pre-cut simulation
- `try/catch InvalidProgramException` для AutoCAD API в headless-среде
- Диагностика в `C:\DB_INS\`
